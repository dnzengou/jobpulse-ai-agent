# Engineering Resume Best Practices

Authoritative reference for `resume-reviewer`, `resume-builder`, and `resume-customizer` agents. Synthesized from the r/EngineeringResumes wiki and template. Conventions assume **United States and Canada**.

> A resume is a 30-second elevator pitch on paper. Its single job is to get an interview. If something on it does not improve interview odds, cut it.

---

## Top-Priority DOs and DON'Ts

These are the rules most often violated. Enforce them strictly.

| # | DO | DON'T |
|---|----|-------|
| 1 | Keep it to **1 page** unless the candidate has 10+ years of experience. | Stretch to 2 pages with filler. A second page is reserved for senior/staff and above. |
| 2 | Lead bullets with strong, **past-tense action verbs** (analyzed, architected, built, designed, reduced, refactored, optimized). | Use weak verbs: *worked on, helped, assisted, participated, used, utilized, gained experience*. Especially never *utilize*. |
| 3 | Write each bullet using **STAR / XYZ / CAR**, with quantified results pulled toward the start. | List job duties. Your resume is not your job description. |
| 4 | **Omit Professional Summary / Objective / Profile** for almost everyone. | Add a summary by default. Only include one for: senior/staff+ engineers (10+ YoE, <2 sentences), career changers, or candidates explaining an employment gap. |
| 5 | **Omit phone number.** Modern interview processes start with email; recruiters will ask for a phone number when needed. | Add a phone number reflexively. Non-local area codes can cause implicit bias. If included anyway: no "Phone:"/"Cell:" prefix and no `+1` country code in US/Canada. |
| 6 | **Omit LinkedIn URL.** It rarely gets clicked; if a recruiter wants your profile they search your name. | Pad the contact line with a LinkedIn link. |
| 7 | Use only **PAID** work in the Experience section (research roles count). Personal/school/club projects belong in `Projects`. | Mix unpaid school projects into Work Experience. |
| 8 | **Tailor for every application** — reorder bullets and surface keywords from the JD. | Send the same resume everywhere. |
| 9 | Show **engineering depth** (calculations, integration, trade-offs, design decisions). | Center the resume on a software tool ("I clicked buttons in SolidWorks"). CAD/tooling should be an "oh by the way." |
| 10 | Use **digits** for numbers (`8`, not "eight"). | Spell out numbers in bullets. |
| 11 | **Spell out obscure abbreviations** the first time (e.g., "scanning tunneling microscope (STM)"). | Assume the reader knows internal/uncommon acronyms. |
| 12 | Proofread with Grammarly / Hemingway / LanguageTool / Quillbot **and** a human. | Ship with typos — they signal lack of attention to detail and cause auto-rejection. |

## Section Order (pick the row that fits)

| Candidate stage | Recommended order |
|-----------------|-------------------|
| Working full-time post-graduation | Work Experience > Skills > Education **or** Skills > Work Experience > Education |
| Student / new grad with some experience | Education > Work Experience > Skills (add Projects before Skills if work experience is thin) |
| No technical work experience | Education > Projects > Work Experience > Skills |
| No work experience at all | Education > Projects > Volunteer/Extracurriculars > Skills |
| Senior / staff (10+ YoE) | Optional <2-sentence summary > Work Experience > Skills > Education (Education at bottom) |

**Never include:** a References section. **Rarely include:** a summary/profile (see DO #4 above).

## Contact Information

Located at the top under the name. Keep it minimal and unformatted.

### Include
- One email address — Gmail or Outlook (avoid AOL/Hotmail/Yahoo). Don't use a college email after graduation unless it's a top-tier school like MIT/CMU.
- GitHub URL **only if** the profile has substantive, README-documented projects (`github.com/username`).
- Personal portfolio URL **only if** it's up-to-date and adds value (`myportfolio.com`).
- Security clearance, if applicable, near your name (e.g., *"Top Secret / SCI eligible with CI Polygraph"*).
- Citizenship/work authorization status if your name or background might raise sponsorship questions (e.g., *"US Citizen"*, *"Canadian Citizen"*, *"US Permanent Resident"*).

### Exclude
- **Phone number** (see top-priority rule).
- **LinkedIn URL** (see top-priority rule).
- Physical address / ZIP code.
- City and state — unless the target role is in that exact city. A non-local location triggers bias.
- An empty GitHub profile.
- More than one email address.
- Personal demographics: age, gender, marital status, children, nationality, ethnicity, religion, political views.

### Formatting rules for contact lines
- Plain text only. No `Email:`, `GitHub:`, or `Portfolio:` labels.
- Strip `https://www.` from every URL.
- Don't underline, italicize, color, or hyperlink-mask the contact items — write them out as plain text.

## Work Experience

### Naming
Section header must be **Experience** or **Work Experience**. Never *Professional Experience*, *Selected Experience*, *Employment History*, *Employment*, or *Job History*.

### Content rules
- **Paid work only** (research roles included). Internships and contract roles must be labeled as such.
- Order positions and bullets by **relevance to the target role**, then by impressiveness — best content first; some readers only get through the first bullet.
- **Add context.** Explain what you did, how, and the impact. Don't dump buzzwords.
- **Differentiate.** A job-description rewrite reads like every other resume. Show accomplishments, metrics, and technical wins.
- **Lead with engineering substance.** Hand-calc sanity checks before hitting RUN in FEA/CFD is the kind of detail engineers respect.
- **New grads:** prove fundamental engineering mastery first. Project-management/leadership content second, only if room remains.

### Bullet point objectives
1. Highlight technical work performed.
2. Highlight technical challenges faced and overcome.
3. Highlight the impact of the work.

### Bullet point structure (use one of these frameworks per bullet)
- **STAR** — Situation, Task, Action, Result
- **XYZ** — Accomplished [X] as measured by [Y], by doing [Z]
- **CAR** — Challenge, Action, Result

If you can quantify the result, **move the metric toward the start of the bullet**.

### Bullet point rules
- 1 sentence per bullet, 1–2 lines long.
- No personal pronouns (*I, we, us, my, our, their*).
- No periods at the end — bullets are not sentences.
- No bullets that wrap onto a new line with only 1–4 words trailing — wasted space.
- No words hyphenated across line breaks.
- Avoid sub-bullets — they clutter and pad.
- Avoid apostrophes (`'`), ampersands (`&`), and slashes (`/`).
- No empty adjectives/adverbs: ~~excellent, innovative, expert, revolutionary, disruptive~~, ~~creatively, diligently, meticulously, strategically, successfully, expertly~~.
- Use digits, not words, for numbers.

### Action verbs
**Strong:** analyzed, architected, automated, built, created, decreased, designed, developed, implemented, improved, optimized, published, reduced, refactored.

**Weak — avoid:** aided, assisted, coded, collaborated, communicated, executed, exposed to, gained experience, helped, participated, programmed, ran, used, **utilized**, worked on.

**Superfluous/awkward — avoid:** amplified, conceptualized, crafted, elevated, employed, engaged, engineered, enhanced, ensured, fostered, headed, honed, innovated, mastered, orchestrated, perfected, pioneered, revolutionized, spearheaded, transformed, leveraged.

**Note:** "Led" is the past tense of "lead." Don't write "lead" for past work.

### Sensitive / proprietary content
Talk about technologies and outcomes without naming forbidden specifics. Example rewrite from the source:

> Instead of: *"Developed C++ software for testing LANTIRN display pod software used on the F-14D Tomcat."*
> Write: *"Developed C++ software for evaluating aircraft subsystems on a [hardware-standard]-based test bench"* — or — *"Created a proof-of-concept integrating COTS items into a data recorder."*

Same logic applies to internal proprietary processes — describe the engineering and metric ("a new process to form composite parts, reducing lead times by 33%") without revealing the IP.

## Education

- Reverse chronological order — master's above bachelor's.
- Use **Bachelor of Science** / **Master of Science** (no apostrophe-s).
- Show graduation date only — no start date, no date range. *Expected May 2025* if still a student; *May 2021* or *2021* if graduated.
- **Don't include coursework** unless the courses are extremely specialized or unusual (e.g., Underwater Autonomous Robotics).
- **Don't include high school.**
- **Don't include schools where you didn't earn a degree.**
- **GPA:** include only if **above 3.75**. 2 decimal places maximum. Remove GPA once you're in your first full-time job and the section moves to the bottom — unless it's still genuinely impressive.
- Don't list school location if the school's name implies it (MIT, UCLA) or location is widely known.
- Don't list awards/scholarships unless they're elite (Rhodes, Fulbright).
- D1/competitive sports may be listed.

## Skills

Section name must be **Skills** — not *Technical Skills*, *Relevant Skills*, etc.

### Include
- Languages you've used thoroughly enough to interview in.
- Frameworks, tools, and programs you've actually used.
- Skills that mirror the job description (and adjacent skills — e.g., listing C++ when applying to Java roles is fine).
- Anything that appears in your bullets — and conversely, every skill listed should also appear (or be implied) in a bullet.

### Exclude
- Soft skills (teamwork, leadership, communication) — demonstrate them via bullets instead.
- Assumed/baseline skills: typing, MS Word, generic IDEs (VS Code, vim), operating systems.
- Code hosting platforms — list the tool ("Git", "SVN"), not the host ("GitHub", "GitLab", "Bitbucket").
- Descriptors like *Expert in*, *Professional in*, or proficiency ratings.

### Formatting
- 3 lines or fewer, single column.
- Order most-important to least-important.
- Group into categories: **Software, Mechanical Design, Simulation and Analysis, Manufacturing, Lab Equipment, Languages, Technologies, Design Tools** — pick what fits the discipline.
- Separate skills with **commas**. Not pipes, hyphens, dashes, or slashes.
- Capitalize proper names correctly: Solid**W**orks, C**ATIA V**5, LabV**IEW**.
- Split related-but-distinct skills: write *"C, C++"* not *"C/C++"*.
- No bolding inside the skills line. The only allowed formatting is the canonical capitalization of the skill itself.

## Projects

Section name must be **Projects** — not *Personal Projects*, *Academic Projects*, *Selected Projects*, etc.

- This section is for **personal, club, and extracurricular work** — never work projects.
- Don't put the word "project" in project titles (it's redundant).
- Capitalize titles correctly using standard title case.
- For personal projects, role/location/dates are usually unnecessary — what matters is the link to a portfolio page or GitHub repo.
- Don't label projects "Personal Project," "Academic Project," or "Group Project."
- Bullets only — never paragraphs.
- Order by relevance to the target role and overall impressiveness.
- Make it real: prefer projects with actual users (even if just you), active maintenance, and visible quality. Avoid trivial tutorial-clone repos.

---

## Portfolios and GitHub

Include only if up-to-date and substantive. An out-of-date portfolio or empty GitHub hurts more than no link.

- Each pinned/listed GitHub project should have a strong README: summary, screenshots, run instructions, **and how to test**.
- Include automated tests (unit / end-to-end) where possible.
- URLs in plain text. Drop `https://www.` (`github.com/bob`, not `https://www.github.com/bob`).

## ATS (Applicant Tracking Systems)

The wiki's stance: **most ATS myths are exaggerated**. Modern ATSs do not auto-reject based on font choice, slight formatting deviations, or whether you have an "exact keyword." Recruiters still read the resume — the ATS just stores and surfaces it.

What this means in practice:
- **Use a single-column layout** — easy to skim and parses cleanly.
- **Standard section names** (Experience, Education, Skills, Projects).
- **Plain-text URLs**, no fancy hyperlink masking.
- **Mirror keywords from the job description** — but write them naturally inside real bullets. Don't keyword-stuff a hidden block.
- **Avoid icons, images, graphics, tables, columns, and text boxes** — for human readability as much as for ATS parsing.

The dominant goal is **human skimmability**. ATS-safety follows from that automatically.

## Bias-Triggering Content (Always Exclude)

Per the wiki, omit anything that can produce negative bias during the resume screen:
- Age / date of birth / graduation year >10 years ago for older candidates' early roles
- Gender, marital status, children
- Nationality / ethnicity / religion / political views
- Photo / headshot
- Non-local city/state when applying out-of-area
- Phone numbers with non-local area codes
- AOL / Hotmail / Yahoo email addresses

## Senior / Staff Engineers (10+ YoE)

- Optional brief summary (under 2 sentences).
- Maintain separate resumes for **management** and **IC** tracks.
- Stay under 2 pages.
- Mention **soft achievements** (mentorship, scope, influence) on top of business results.
- Mention not just impact, but **influence**.
- Compress earlier roles aggressively — recent work gets the bullets.
- Move Education to the bottom.

---

## Career Changers

- Include a 2-sentence summary explaining the transition and motivation. This is one of the few cases where a summary helps.
- Link to working projects and source code.
- Be concise about prior careers.
- Aim for 1 page.

## Common Pitfalls (Quick-Scan Checklist for Reviewers)

When reviewing a resume, flag any of these:

- [ ] Has a "Professional Summary" (without justification — senior, career-changer, or gap)
- [ ] Has a phone number
- [ ] Has a LinkedIn URL
- [ ] Has a physical address or ZIP
- [ ] Has a non-local city/state
- [ ] Uses AOL/Hotmail/Yahoo email
- [ ] Has more than 1 email
- [ ] Has a "References" section or "References available upon request"
- [ ] Has personal demographics (photo, age, marital status, etc.)
- [ ] Multiple pages without 10+ YoE justification
- [ ] Bullets start with weak verbs (worked on, helped, used, **utilized**, assisted)
- [ ] Bullets are job-description copy, not accomplishments
- [ ] No quantified results in bullets
- [ ] Personal pronouns (I, we, my)
- [ ] Periods at end of bullets
- [ ] Soft skills in the Skills section
- [ ] "GitHub", "GitLab", "Bitbucket" in Skills (should be "Git")
- [ ] Section named *Technical Skills*, *Professional Experience*, *Personal Projects*, etc.
- [ ] Coursework listed (unless extremely specialized)
- [ ] High school listed
- [ ] GPA below 3.75 listed (or any GPA after first full-time job, unless elite)
- [ ] Apostrophe in "Bachelor's" / "Master's"
- [ ] Date ranges using hyphens or "to" instead of en dashes (–) with spaces
- [ ] Mixed date formats (semester names, abbreviated years like '23, numeric months like 9/2013)
- [ ] Tables, columns, icons, graphics, or images
- [ ] Justified text (causes uneven word spacing)
- [ ] Indented sections / bullets (bullets already indent themselves)
- [ ] Walls of text instead of bullets
- [ ] Sub-bullets cluttering content
- [ ] Empty adjectives/adverbs (excellent, expertly, etc.)
- [ ] Spelled-out numbers ("eight" instead of "8")
- [ ] Typos / grammar errors

## Customization Principles

When tailoring a resume per the `resume-customizer` agent:
- Mirror the JD's vocabulary and keywords inside real, accurate bullets.
- Reorder bullets within each role so the most relevant work is first.
- Reorder roles only if relevance differs dramatically from chronology (rare).
- Re-prioritize the Skills list to surface JD-matching skills first.
- **Never fabricate experience** — only reframe and re-emphasize what's already true.
- Preserve all factual content; change emphasis and ordering only.
